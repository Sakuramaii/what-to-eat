# 今天吃什么

以聊天为中心的中文用餐助手。桌面左侧 25% 放用餐条件，中间 50% 放 AI 对话和输入框，右侧 25% 列出符合条件的全部候选，推荐方案置顶，每张卡片直接展示距离、价格、味道、饭量和吃完速度五项文字指标。历史与记忆收进“记录与偏好”二级入口。原生 HTML/CSS/JavaScript + Python 标准库 + SQLite，无需安装项目依赖。

## 启动

需要 Python 3.10 或更新版本。

~~~bash
cd /data/users/liuhongwei/eat
python3 server.py
~~~

浏览器访问 **http://127.0.0.1:8000**。如果项目运行在远程机器，请先将远程端口 8000 转发至本机。端口被占用可运行 **python3 server.py --port 8001**。Ctrl+C 停止服务。

首次只在推荐栏按你的食堂统计展示标注为“灵感预览”的基础规则方案，不自动请求付费 AI。中间输入框提供三种模式，点击发送或按 Enter 开始，Shift+Enter 换行。

- **聊一聊**：普通 AI 对话，保留最近的聊天上下文，回复在中央显示；同时提取本次用餐条件并更新右侧全部候选，AI 选择的方案置顶。聊天不会自动记餐。
- **帮我选一餐**：从文字提取条件，结合左侧设置筛选；中央解释首选，右侧列出全部可行候选，推荐项在前，支持搜索餐厅与餐品。无文字时按当前条件推荐。失败后可主动选择基础规则。
- **记忆反馈**：描述餐后感受，AI 提取后直接保存并参与学习；明确提出的长期偏好也直接更新，不再确认。保存后立即按最新偏好刷新右侧推荐。仅保存已表达的信息，感受与等待时间均可留空；历史等待时间不会被当成下一餐的时间限制。

三个模式每次发送都会更新右侧，无需切换模式。普通聊天在同一次模型调用中完成回答、条件提取及推荐，避免额外串行请求；模型只返回文字时仍可聊天，右侧明确显示为基础规则推荐。模型超时或返回错误时保留输入和重试入口，同时提供标注清楚的基础规则候选。在记录抽屉中手动调整偏好后，右侧也会自动重新排序。

“想吃面”等明确餐品要求会保存为本次 foods 条件，与清淡、香辣等口味标签分开；“不吃拉面”保存为 avoid_foods，不当成配料过敏。多个想吃的餐品表示任选其一，可在“调整用餐条件”中直接修改。服务端先按餐品要求筛选，再比较预算、口味和用餐间隔；候选不足时不拿其他品类凑数。选餐模式的推荐调用同时传入原始用户消息和聊天上下文，模型按匹配程度排序后的第一项就是首选，不再被本地综合分替换；所有菜品 ID 和金额仍由服务端校验。无用餐记录只代表未知，不能据此声称从未吃过。

用餐条件默认折叠，通过左侧“调整用餐条件”或输入框“条件”打开。预算、时间和人数同时支持拖动滑条和直接输入；清空输入或将滑条拉到最左端即为未设置。聊天会自动把需求同步到条件栏，再筛选右侧候选。首次打开及新对话后，预算、时间、人数、目的均留空，口味、忌口及推测条件清空，饭量和节奏恢复为不限，完全没有提及的字段不填默认值。

明确数字直接采用，也能识别“人均二十元、半小时、我们俩”；模糊表达主动推测，例如“十几块”暂按 15 元、“有点赶”暂按 20 分钟、“和室友一起”暂按两人、“没胃口”暂按少一些。“再便宜一点”会结合本餐已有预算调整。推测值显示标记和可展开的依据，并立即参与推荐，不要求再次确认；手动输入、拖动或之后明确纠正会覆盖对应推测。没有提及的新字段保持原值或留空；餐后历史描述不当成下一餐条件，只有明确提出下一餐要求时才更新。

未说明人数时，按单份参考展示价格、菜品和组合，不代表独自用餐；说明人数后按人数计算份数与人均金额。饭量描述不代表具体克数；可设置“少一些／适中／吃饱”和“慢慢吃／正常／快点吃”，未指定时均不偏向某一档。菜单点餐视为已经到店。手机端两侧收为可打开的侧栏。

在“帮我选一餐”中实际发起选餐后，首选方案自动记为已吃，无需再确认；右侧点击“换成这份”、修改菜品数量或在选餐模式中“换一批”都会替换本餐，不新增记录。普通聊天与记忆反馈中的自动推荐、“换一批”只更新候选，保留当前模式及已有用餐记录；明确选中一份才会记餐或改选。反馈完全自愿；误记时可在历史中点“没吃这餐”，并从对话中恢复。

同一浏览器会话内，三小时内的连续改选视为同一餐；发送餐后反馈或超过三小时后，下一次选餐建立新记录。刷新保留对话文字及当前用餐选择，不重复记餐；首页灵感预览和普通聊天不会记餐。

点击 **新对话** 清空当前聊天消息、模型对话上下文和本次用餐条件，无需再次确认。上一餐由服务端标记为已完成，页面明确提示“上一餐已完成，现在开始新一餐”；历史中也显示完成状态。用餐历史及反馈、自动学习和手动偏好作为长期记忆保留，后续推荐仍会使用。右侧按空白条件、长期偏好和用餐间隔重新展示食堂候选。下一次选餐建立新记录，服务端拒绝旧会话或旧记录 ID 覆盖已完成餐次；仍可补填或修改上一餐反馈。重复点击新对话不会新建用餐记录，也不会依次结束更早的历史餐次。已上传菜单和模型选择保留，退出当前菜单点餐场景。新对话后的第一次请求不再携带旧聊天消息，刷新后旧消息和旧条件也不会恢复，过期页面中的旧餐次也不会恢复为当前选择。请求失败时保留当前内容并显示提示。若需删除长期记忆，可在“记录与偏好”中单独管理，或使用需确认的“清空本地记录与偏好”。

输入框下方的模型按钮显示当前 LLM。点击可搜索并选择并行科技账户目录中的对话模型，选择保存在当前浏览器中。切换作用于之后的聊天、需求解析、推荐和反馈，不需要重启，也不会改变其他浏览器或服务默认模型；历史回复保留原模型标记。请求进行中不能切换模型。

目录在打开选择器时读取，支持手动刷新，并过滤图片、视频、语音和向量模型。目录读取失败会明确显示常用模型列表；目录可见不代表所有模型均有调用权限，失败时保留选择和输入，不自动改用其他模型。

## 发送自己的菜单

点击输入框旁的 **发送菜单**，上传照片、截图，或粘贴“菜名＋单价”文字；也可将菜单图片拖入上传区域，或直接粘贴到聊天输入框。一次最多 3 张 JPG／PNG／WebP 图片、60 道菜，单张原图最多 12 MB，浏览器会先缩放压缩。可同时填写“两个人人均 30 元、搭配荤素”等需求，并设置预计等待和用餐时间。

点击 **识别并选菜** 后，AI 读取菜名、价格并提出搭配；服务端按识别单价重新计算总价与人均、检查预算及时间，再在中央回答和右侧展示推荐组合。共享菜搭配主食，单人套餐按人数分配，份量仍需向店家核实。单纯上传不记餐；后续“帮我选一餐”或明确选中一份按原有记餐规则处理。

识别完成后，输入框上方会显示当前菜单。三个聊天模式均继续围绕这份菜单调整；点击菜单名称可修正菜名、单价、菜品类型、配料和时间。未标价、时价或价格区间不补造金额，补填价格后才参与推荐。有忌口时，未核实配料的菜品不会进入推荐：请向店家核实，在编辑菜单中补充配料并勾选“已核实”。等待及用餐时间默认估计为 10＋20 分钟，可自行修改。

菜单识别结果保存在本地 SQLite，刷新或重启后可复用；图片只用于本次识别，不落盘、不写入聊天存储。点击 **发送菜单** 可使用之前的菜单，点击输入框菜单标签上的 × 可退出。删除菜单保留原有用餐记录及当时的价格快照；“清空本地记录”会同时删除已上传菜单。

图片识别使用单独的视觉模型，默认 **GLM-4V-Plus-0111**，后续聊天使用输入框中选择的 LLM。图片识别失败时保留原图和文字，可重试或粘贴文字菜单。识别结果可能有误，支持直接修正；本功能不读取实时商家信息。

## 并行科技配置

密钥优先从 **PARATERA_API_KEY** 环境变量读取；未设置时读取现有 muzzle 配置。不会将密钥复制到项目、返回浏览器或写入日志。

上传 GitHub 时保留 `canteens.tsv` 中的食堂基础数据；API key 文件不提交。`.gitignore` 已排除 `.env`、本地 `auth-profiles*.json`、常见密钥文件、凭据目录、运行数据库和调试产物。默认凭据文件位于项目外的 `~/muzzle/config/auth-profiles-4.json`，无需复制进仓库。

| 环境变量 | 默认值 |
| --- | --- |
| PARATERA_MODEL | GLM-4-Flash |
| PARATERA_VISION_MODEL | GLM-4V-Plus-0111，用于菜单图片识别 |
| PARATERA_BASE_URL | https://llmapi.paratera.com/v1，仅允许该官方地址 |
| PARATERA_API_KEY | 未设置则尝试现有本地配置 |

本地配置按 profiles → 配置名称 → key 读取。请在启动服务的终端中设置环境变量。标准非流式 chat/completions 调用，不依赖模型工具调用或原生 JSON 模式。模型可用性与权限以账户为准；失败时显示错误并保留输入，可重试或主动切换基础规则。

## 数据与推荐规则

- 默认目录使用你提供的 **52 条有完整描述的常吃餐品／窗口，覆盖 11 个食堂**。原始统计保存在 canteens.tsv，5 条带星号、没有指标信息的记录不参与推荐。原有虚构餐厅、菜品、价格和耗时已从应用目录移除；校外场景需发送自己的菜单。
- 启动时将统计导入 SQLite 的 canteen_entries 表，之后从数据库读取。五项指标均为 TEXT 列；旧数字档位、历史用餐快照与餐后评价会自动迁移为文字，保留记录 ID、时间、原始意见、学习来源、手动偏好和上传菜单。迁移前已备份实际数据库；“清空本地记录”也保留这份基础食堂目录。
- 距离使用“远／较远／适中／较近／近”，价格使用“贵／较贵／适中／较便宜／便宜”，味道使用“不好吃／不太好吃／一般／好吃／很好吃”，饭量使用“少／较少／适中／较多／多”，吃完速度使用“慢／较慢／适中／较快／快”。这些描述来自个人评价，味道描述不代表已知清淡、辛辣等口味类型；速度不代表排队或出餐快慢。饭量和速度按本次目标取舍，不默认越多越快越好。
- 价格按原区间保留：便宜 ≤10 元，较便宜 >10–15 元，适中 >15–20 元，较贵 >20–25 元，贵 >25 元。预算为人均上限；按区间上限核验，区间跨过预算的选项放在末尾并标注“待核价”，不自动推荐或记餐。详情中可补充本餐实际单价，服务端按整数分重算并核验预算，不用区间中点冒充实际价格。
- 食堂统计未提供具体步行、等待和用餐分钟数，时间仅作为参考，页面明确提示无法保证分钟限制；不把文字档位换算成虚构耗时。上传菜单仍按手动设置的时间估计核验。
- 忌口按菜名和已核实食材匹配。统计未包含配料，有明确忌口时不会假定安全，需发送并核实配料菜单后再推荐；“不吃辣”仍提取为避免“辣椒”。
- 服务端先过滤硬限制，再让 AI 选择有效方案 ID、说明取舍；模型价格不参与计算，解释中的数字不会作为事实展示。
- 本次需求优先于长期软偏好；按每道菜最近一次用餐的真实日期计算间隔，明显偏向久未吃过或尚无记录的餐品。间隔在 0–30 天内逐步增加权重，仍先核验预算和忌口。
- 右侧保留当前条件下全部候选，最多三个推荐项置顶，其他项结合主观描述、用餐间隔和本次饭量、节奏排序，待核价项放在末尾。“换一批”优先更换已推荐组合；候选不足时按实际数量返回。未设预算时列出 52 条；明确设置人均 25 元时可选 42 条，>25 元的 10 条需更高预算才显示为待核价。明确人数后每人分配一份，详情可调整数量。
- 数据持久化在 **data/eat.sqlite3**，已忽略版本控制。启动参数 **--db /绝对路径/test.sqlite3** 可选择独立数据库。
- 首版仅供本机单用户使用，监听回环地址，不包含登录、支付下单、实时商家数据或在线部署。

## 自动学习与撤销

每次用餐最多有一份反馈，补充会合并已提供的字段，修改感受会替换旧信号。口味“好吃／很好吃”为正向，“不好吃／不太好吃”为负向，“一般”为中性。只有口味感受影响口味与品类偏好；分量满意度、性价比、等待时间及补充意见独立记录，不补造未表达的感受。分量评价使用“很不满意／不太满意／一般／满意／很满意”，性价比使用“不划算／不太划算／一般／划算／很划算”。分量满意度与餐品的饭量多少分开记录。

第一次明确的口味反馈即可形成软偏好，无需确认；多次反馈按正负方向的多数更新，相等时不偏向任一方向。整体口味感受作用于组合中的口味和品类，每个标签在一次用餐中只计一次。临时需求和仅默认记餐不会直接变成偏好，也不会生成硬性忌口。

在偏好面板查看来源、手动修改、反转或删除；删除抑制该标签，直到选择“恢复自动学习”。手动设置优先于自动学习。在历史中撤销／恢复单次学习会重算自动偏好，保留原始反馈。清空本地数据需要输入确认文字。

## 接口

写接口接收 JSON。目录和金额均由服务端校验。

| 接口 | 用途或请求体 |
| --- | --- |
| GET /api/catalog | 已导入的食堂文字描述目录、上传菜单及选项；source=personal_descriptions、sample=false |
| GET /api/status | 密钥是否配置，不请求上游 |
| GET /api/models | 账户对话模型目录、default_model、source；加 ?refresh=1 强制刷新，读取目录不发送生成请求 |
| GET /api/state | 历史、偏好和计数 |
| POST /api/new-chat | {active_meal_id?}；标记上一餐已完成，返回 completed_meal_id、state、空白 needs，以及结合长期偏好和用餐间隔的基础规则 recommendations；保留历史、反馈和偏好，浏览器清空聊天上下文和临时选餐会话 |
| POST /api/chat | {text, messages: [{role, content}], mode: "chat" / "feedback", needs?, meal_id?, active_meal_id?}；返回 reply、最新 needs、recommendations，反馈模式另含 saved_feedback、saved_memory 和最新 state；推荐刷新始终不记餐 |
| POST /api/menus/import | {text?, images?: [data:image/...;base64,...], requirements?, needs, model?, vision_model?, wait?, dine?}；返回 menu、needs、recommendations、venues、recognition_model，不记餐 |
| POST /api/menus/update | {menu_id, menu, needs}；菜单价格输入单位为元，返回的 price 为整数分；编辑后重新校验并更新推荐 |
| POST /api/menus/delete | {menu_id}；删除菜单，保留已保存用餐快照 |
| POST /api/parse | {text, needs, mode: "ai" / "basic"} |
| POST /api/recommend | {needs, mode, text?: 原始用户消息, messages?: 当前聊天上下文, exclude?: [方案ID], record?: true, meal_session?: 本餐标识}；返回最新 needs；record 默认为 false，仅实际选餐传 true 并指定会话，重复请求更新同一餐 |
| POST /api/quote | {venue_id, items: [{dish_id, quantity}], needs, actual_prices?: {菜品ID: 本餐实际单价元数}}；仅个人食堂记录支持补充本餐价格 |
| POST /api/meals | 同 quote，加 meal_id 修改本餐；新记录可指定 meal_session 或 request_id，相同标识不重复创建 |
| POST /api/meals/cancel | {meal_id, cancelled: true / false}；撤销或恢复记录，同步影响间隔与学习 |
| POST /api/feedback | {meal_id, feedback: {taste?, portion?, value?, wait?, note?}}；taste/portion/value 为上述文字评价，wait 为分钟数；至少一项，直接保存 |
| POST /api/learning | {meal_id, enabled: true / false} |
| POST /api/preferences | {tag, direction: 1 / -1 / 0}，或 {tag, action: "reset"} |
| POST /api/reset | {confirm: "清空本地记录"} |

needs 字段：scene（canteen/outside/menu）、venue_id、budget、minutes、people、tastes 数组、avoid 食材数组、foods 想吃的餐品数组、avoid_foods 不想吃的餐品数组、purpose、portion（不限／少一些／适中／吃饱）、pace（不限／慢慢吃／正常／快点吃）、inferred（推测来源字典，键为字段名，值含 value 与 reason）。budget、minutes、people 未设置时为 null，purpose 为 ""；省略字段也保留未设置状态。推荐返回 plans（最多三个推荐）、options（包含待核价项，recommended 标识）、primary_id、mode、conflicts、exhausted、notice；记餐时另含 meal_id、state。price_basis 为 person 时金额为人均，为 serving 时按参考份量计价、people 为 null，不将人数补为 1。个人食堂记录的 rated=true、ratings 为五项文字描述，descriptors 为各指标的文字档位列表；未提供实际单价时 total/per_person 为 null，total_low/high 和 per_person_low/high 为整数分区间，开放上限为 null，minutes 等时间为 null；needs_price_check=true 时禁止记餐，需补价或调整预算。异常返回 error 和 code；对话上游失败时同时返回只读的 recommendations 与 needs，页面保留错误提示和输入。

/api/chat、/api/parse、/api/recommend 可传可选 model 字段，使用平台的完整模型 ID；未传时使用 PARATERA_MODEL，默认 GLM-4-Flash。聊天与 AI 推荐响应包含实际使用的 model，基础规则不调用 LLM。
